# She — one-tap Android app for the She web app in Termux

**She** is a small clumsy AI (Furret icon) that lives in a webpage.
The webpage is the face; the brain and the shell live in Termux on the
phone — a llama.cpp server running the user's GGUF, plus `kali-bridge.js`
(Node) on `127.0.0.1:8080`.

Tap the **She** APK icon → it starts Termux in the background
(`bash ~/.she/start.sh`), waits for the bridge, then opens the webpage
in a WebView. No energy wasted on image generation here — the icon is
the Furret image Alex supplied.

## What was fixed (2026-11-11)

**The bug — confirmed in the source:** `kali-bridge.js` had **no shell
execution at all**. `CODING_NOTES.md` said it plainly: *"Running
commands from chat requests is not wired in."* So the LLM literally
could not run Kali/Ubuntu commands — it could only talk about them.

**The fix — `POST /shell` in `source/kali-bridge.js`:**
- Local-only (`127.0.0.1`), token-gated: header `X-She-Token` must
  match `SHE_TOKEN` env (generated by `start.sh`, passed to the
  WebView by the Android app — never hardcoded in source).
- Allowlist only: `ls, pwd, whoami, uname, date, echo, cat, grep, find,
  ps, df, free, uptime, which, hostname, head, tail, wc, sort, lsblk,
  ip, ss`, plus exactly `nmap --help` and `apt list --installed`.
- Rejected with 403: anything with `; && || | \` $() > >> <`, and
  `rm, sudo, curl, wget, chmod, mv, cp, dd, kill`, etc.
- Run via `child_process.spawn` with an argv array — never `exec()`
  with a shell string. 10s timeout, 64KB output cap, cwd = `$HOME`.
- Live-tested in this VM: `ls` → 200 with output; `rm -rf /`,
  `ls; id`, and a missing token → all 403.
- The LLM is told in its system prompt (`personality.js`) to reply
  with one fenced ` ```shell ` block when asked to run a command,
  and **not** to claim it ran unless a tool result came back.
- `index.html` shows a **"Run in Termux"** button when a reply
  contains a ` ```shell ` block; output streams into the page.
  `/prompt` and `/state` behaviour is untouched.

**Model default fixed:** `MODEL` now defaults to
`josiefied-qwen2.5-3b-instruct-abliterated-v1-q4_k_m.gguf` via the
llama.cpp server (`LLAMA_URL` default `127.0.0.1:8090/v1/chat/completions`),
**not** `qwen2.5:1.5b`. Ollama stays as fallback only.

**`source/start.sh`** (place at `~/.she/start.sh` in Termux):
starts `llama-server` with that GGUF on 8090 if not already running,
then `node kali-bridge.js` on 8080, logs to `~/.she/she.log`,
idempotent (does not start duplicates).

## Termux setup on the phone (do this once, before installing the APK)

1. Install **Termux** (Play Store / F-Droid) and **Termux:API**.
   Open Termux at least once.
2. In Termux:
   ```
   pkg update && pkg install nodejs openssl
   mkdir -p ~/.she/models
   ```
3. Copy `source/` to `~/.she/` on the phone (e.g. `scp`, USB, or
   Termux's storage access), so you have `~/.she/kali-bridge.js`,
   `~/.she/index.html`, `~/.she/start.sh`, etc.
   ```
   chmod +x ~/.she/start.sh
   ```
4. Place the GGUF at:
   ```
   ~/.she/models/josiefied-qwen2.5-3b-instruct-abliterated-v1-q4_k_m.gguf
   ```
   (or edit `MODEL_PATH` in `start.sh` to point at where it actually is.)
5. Install **llama.cpp** in Termux so `llama-server` is on PATH, or
   place the binary at `~/.she/llama.cpp/llama-server` or
   `~/.she/llama-server`. The package name varies by Termux build —
   if `pkg install llama-cpp` does not exist, build llama.cpp from
   source in Termux. Without it, the bridge still starts and falls
   back to Ollama if Ollama is running.
6. Verify once, manually, in Termux:
   ```
   bash ~/.she/start.sh
   curl http://127.0.0.1:8080/state
   ```
   You should get `{"x":…,"y":…,"mood":"…","esc":…}`. Check
   `~/.she/she.log` if it does not answer.
7. **Then** install the She APK and tap it — it does steps 6's
   startup for you from then on.

## What the APK does on tap, step by step

1. Checks Termux (`com.termux`) is installed. If not, shows a
   message with a Play Store link.
2. Generates a random shell token, and fires the Termux
   `RUN_COMMAND` service: `SHE_TOKEN=<token> bash $HOME/.she/start.sh`
   in the background. (Requires the `com.termux.permission.RUN_COMMAND`
   permission, declared in the manifest.)
3. Shows "Starting She…" with the Furret icon, polling
   `http://127.0.0.1:8080/state` for up to 60 seconds.
4. Loads the bundled `assets/.she/index.html` in a WebView
   (JavaScript + DOM storage on, cleartext allowed only to
   `127.0.0.1`/`localhost`). The page is the face of the app.
5. When She replies with a ` ```shell ` block, a **Run in Termux**
   button appears; tapping it POSTs to `/shell` with the token the
   app injected via the `SheBridge` JavascriptInterface, and the
   output appears under the reply.

## Assumptions made (stated, not guessed silently)

- **Termux paths:** `~/.she/` is the home for everything; the GGUF
  is at `~/.she/models/josiefied-qwen2.5-3b-instruct-abliterated-v1-q4_k_m.gguf`;
  `llama-server` is on PATH or at `~/.she/llama.cpp/llama-server` /
  `~/.she/llama-server`. Edit `start.sh` if any of these differ.
- **"Kali":** as Alex said, this is not a Kali install — it is
  Termux (Ubuntu-style Linux) with Kali-style commands. The
  allowlist is read-only/diagnostic commands that exist in Termux;
  `nmap`/`apt` are included as named, but `nmap` may need installing
  in Termux (`pkg install nmap`).
- **Termux RUN_COMMAND:** the APK uses the documented
  `com.termux.RUN_COMMAND` service intent with
  `RUN_COMMAND_PATH` = Termux bash and `RUN_COMMAND_ARGUMENTS`.
  This is the standard mechanism; it needs Termux to have been
  opened at least once, and on some Termux versions the user must
  allow the app to run commands (a one-time Termux prompt).
- **Token passing:** the token is generated fresh by the APK on
  every launch and passed in the command line to `start.sh`. If
  `start.sh` is run manually, it generates/keeps a token in
  `~/.she/token` (0600) instead.
- **Icon:** the supplied Furret image is a 475×475 JPEG on black.
  It is used as-is (resized per density, black adaptive background)
  — no AI generation was used for it.
- **WebView file→http:** the bundled page is `file://` and fetches
  `http://localhost:8080`. The app enables
  `allowUniversalAccessFromFileURLs` for that; the bridge still
  requires the token for `/shell`, so other pages cannot use it.
